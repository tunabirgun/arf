Ownership

Your data, actually yours

A folder of files that outlives the app.

The single promise Arf will not break is that your work belongs to you, in a form no company controls. Your vault is a plain folder: one Markdown file per note, an attachments/ folder holding the PDFs, EPUBs, and images you add — reference files beside it, note images in attachments/images/ — and a small header on each note. You choose that folder at first launch, and the app — native on Windows, macOS, and Linux — reads and writes it directly on your disk. Copy it to a USB stick, keep it in a Drive or Dropbox folder, open it in any editor, and it still makes sense. Everything Arf builds on top of the files — the search index, the similarity vectors, the graph's pinned positions, the order you dragged things into — can be rebuilt or re-made at any time. None of it is ever the only copy of anything you wrote.

The header on each note

Every note carries a short YAML header: a stable id, its title and tags, and two timestamps for each of created and updated — one in UTC as the universal standard, one in your machine's local time with its offset (…+03:00 in Istanbul). Arf reads your system's time zone, so the record is correct wherever the note was written, and the UTC field keeps sync ordering unambiguous across devices.

Bringing notes in

Settings → Import and export reads notes written elsewhere. Choose single Markdown files, a whole folder, or a ZIP archive; a folder can be an Obsidian or Jekyll vault. Each note keeps the folder it sat in, its frontmatter title, tags and dates are read where present, and, when you import a folder or a ZIP archive, the images the notes show are copied into the vault's attachments/images/ folder with the links pointed at the copies. Obsidian image embeds such as ![[figure.png]] become standard Markdown images. Hidden folders such as .obsidian and .trash are skipped.

References come in the same way: a BibTeX, RIS or CSL-JSON file adds its entries to the Library, and an entry already there (the same DOI, or the same title, first author and year) is skipped. You can also drop any of these files, or an .arf bundle, onto the Arf window. A line under the buttons reports how many notes were added or merged and what was skipped.

Taking it all out

Export as ZIP writes the vault as an ordinary archive: every note as a Markdown file in its folder, the Library as references.bib and references.json, and, in the desktop app, the vault's images and attached PDFs and EPUBs under attachments/, with a short README. Any Markdown tool can open it, and importing it into Arf restores the notes, references and files.

An .arf file is the other way to carry the vault: one file with every note, folder and reference, for a dated backup or for handing the vault to a collaborator. Import it with Import .arf….

Sync across your devices

Because your vault is an ordinary folder of Markdown files, syncing it needs no account with Arf and no server of ours. Keep the vault folder you chose at first launch in a place your devices already sync — Dropbox, iCloud Drive, OneDrive, Google Drive, or Syncthing. Point Arf at the same folder on each machine and you are done.

Choose the folder once. Arf keeps it in step — both ways, automatically, while you work.The sync flow, in one sentence

Arf watches the folder continuously. An edit you make on your laptop appears on the desktop within seconds; a note you delete on one device is removed on the others. There is no button to press and no command line — the cloud service you already use moves the files, and Arf reconciles them by keeping the newer version of each note. The header at the top of the sidebar shows the vault's folder name with a small live sync indicator beside it. Power users who prefer real version history can put that same folder in a git repository and commit underneath.

The desktop app lists the vault folder with a single native call on every check and reads again only the files whose size or modification time changed, so a large vault is not re-read every few seconds. A Markdown file without Arf's header is dated by its modification time, so it is not treated as changed on every check and is not rewritten. An edit made in another editor updates the note's links, tags and graph even when it left the note's updated time alone.

The local cache

The files on disk are the vault. Arf also keeps a copy of your notes in the app's IndexedDB storage, one entry per note, so the notes appear at launch before the folder has been read, and a recent edit that had not yet reached the folder when the app closed can be restored. Because the entries are stored per note, large vaults no longer reach the browser's storage limit, which in Arf 2.0 could show a false "Couldn't save" warning above about 1,500 notes. A note you delete is removed from this copy as well, so it does not come back at the next launch.

What happens to your notes

Notes are the thing you cannot afford to lose, so every operation that touches a file is written to be safe rather than fast. Concretely:

When you…What Arf does
Rename or move a noteWrites the new file first and removes the old one only after the write succeeds — a note can never end up on neither path. A failed write (locked file, reserved name, path too long) leaves the note where it was and retries on the next sync tick. Notes are identified by a stable id in their header, not by filename, so renaming or moving the .md file yourself never loses it.
Move a folderRewrites the paths of its notes and subfolders in one step. A circular move into its own descendant, and a move onto a name another subtree already owns, are both refused — two folders are never silently merged.
Hit a sync conflictKeeps the newer copy of each note. If the note open in the editor also changed on another device, the remote version is kept beside yours as a (conflict copy) rather than overwritten, so you choose which to keep. A note deleted elsewhere is tombstoned so it is not resurrected; a delete that could not complete is retried.
Delete a note or referenceAsks for confirmation first. The note's file is removed from the vault folder and its entry from the local cache, so it does not reappear at the next launch.
Import notesMerges by id: when a note with the same id is already in the vault, the newer of the two copies is kept, and a file imported a second time is recognised. Imported notes are written into your current vault, not tied back to the file they came from. References already in the Library are skipped.
Back up or exportWrites the vault to a ZIP archive or an .arf file, or a single note to Markdown, HTML, or PDF, as a separate file; the vault itself is not touched. If the save is cancelled or the target is not writable, Arf tells you and leaves everything as it was.

If the local cache ever cannot be read, Arf leaves it untouched and loads your notes from the files on disk.

Export your writing

Notes leave as easily as they arrive. Any note exports to Markdown, HTML, or PDF, and each format shows only the options that fit it — a Markdown export asks whether to keep the YAML header, a PDF export asks for page size and margins — so you are never faced with page settings for a plain-text file. The document export is built to avoid the things that make an exported file look broken:

  • No orphaned headings — a heading is kept with the paragraph that follows it, so none is ever stranded alone at the bottom of a page.
  • Images that fit — pictures are centered and scaled to the page, keeping their proportions, and code blocks are fit to the width instead of spilling past the margin.
  • Your typography, preserved — the page keeps its EB Garamond setting, with page size and margins under your control.

Citations in the document resolve through the Library, so a manuscript exports with its reference list intact. A note's images travel with it too: the export inlines them, so the file you hand off is self-contained. A small Arf mark sits in the top-right corner of the page — and nothing else, no running header or footer.
